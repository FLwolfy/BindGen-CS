# BGCS 3.0.0

## Architecture and extensibility

BGCS 3.0 is a new major version with eleven implementation projects and one public
`BindingHost` pipeline for the CLI, embedded SDK and workspaces.
Native facts, C++ bridge operations, final interop contracts and managed presentation
have separate immutable models. Contracts and Runtime have no generator implementation
dependencies.

Ordinary plugins reference `BGCS.Contracts` and use typed source, target, transform,
lowering, projection/backend, source contribution, artifact processing and validation ports.
Extension state and declared inputs participate in cache identity. Parser-specific
contributors use the separate version-pinned, worker-only Advanced Clang interface.

Old generator APIs and flat configuration readers are removed. There are no legacy
aliases, compatibility wrappers, migration tools or migration files. Use `init` to
create a current grouped configuration and the [current usage guide](../getting-started.md).

## Parser portability

Clang parsing runs in an isolated worker by default. Worker protocol/model identities,
native parser resources and builtin headers are validated together. Host parser assets
are separate from target SDK headers, sysroot, toolchain and ABI facts. The worker parses
against explicit target inputs; generated bridge headers are reparsed and checked against
the neutral contracts. The product does not execute an external native preprocessor or
compiler. Consumers compile emitted source assertions with their actual compiler and
independently verify binary behavior; that compiler need not be Clang.

Unknown ABI or lifetime facts remain unknown. Equal sizes do not establish safe by-value
calls. Unsupported cases are rejected or require an explicit pointer/bridge/shim route.

## Verification and packaging

Four products are intended for users: `BGCS` (complete generator SDK),
`BGCS.Contracts`, `BGCS.Runtime` and `BindGen-CS`. Internal modules are delivered by the
SDK/tool; RID tool shards and parser runtime supplements are distribution details.
The SDK/tool include the built-in C/C++ analysis, lowering and bridge source generation.
Consumer build systems compile, link and deploy native libraries and generated bridges.

The default output is an instance API with FunctionTable imports and split managed
files. DllImport, LibraryImport, explicit shared static APIs, single-file output and
Runtime source delivery remain available. Owned publication, complete input fingerprints,
final emitted-contract checks and candidate validation preserve the previous complete
output on required failure.

C++ uses typed bridge operations, explicit template instantiation, finite standard/custom
family protocols, checked inheritance casts and exception boundaries. Finite variadic
adapters expose fixed ABI signatures. Raw native holders and friendly managed collection
returns are distinct capabilities; ownership, encoding, allocator and callback shutdown
semantics still require adequate facts or explicit project contracts.

Publication is gated by the exact revision's required core generator and installed
product evidence, followed by physical package verification, signed provenance and public
NuGet payload/installation checks. These notes describe versioned contents; they do not
substitute for actual release assets, CI results or package availability.

## Requirements and scope

- Generator, Runtime and default consumers require .NET 10; source uses C# 14.
- Native language defaults are C17 and C++23. BGCS generates sources; it does not build
  consumer projects or compile, link, package or deploy native libraries.
- Runtime delivery defaults to the package. Source mode is independent of the generator;
  single-file managed output defaults to `Bindings.cs`.
- Static adapter capabilities preserve `library.nativeName`. Consumers must register or
  link that exact module name; `__Internal` is used only when explicitly configured.
- Required CI is Windows full generator checks, Linux/macOS generator smoke and one full
  product-install job. Original per-host performance budgets remain. AOT/Wasm application
  builds are optional manual private checks; target facts and source generation remain.
- Nonblocking profiles currently retain the raw C++ virtual proxy protocol while omitting
  owning managed virtual registration. Ordinary C retained/async browser protocols do not
  establish that separate full-native-frame shutdown guarantee.

See [capabilities](../capabilities.md), [architecture](../architecture.md),
[configuration](../configuration-guide.md) and [Runtime lifetimes](../runtime-lifetime.md)
for the supported protocols and their limits. Arbitrary C++ libraries are not promised
automatic, zero-configuration C# API design.

## Provenance

The release workflow authenticates the accepted main revision, required job/artifact
evidence and physical package bytes before creating or validating the immutable
`v3.0.0` tag. It then publishes with NuGet trusted publishing, verifies public package
payloads and clean four-product consumption, and attaches SPDX/SLSA records and GitHub
OIDC attestations. Historical tags or dirty local tests do not certify this release.

The English naming vocabulary and Clang resources retain their pinned sources, licenses
and content digests. Current requirements are defined by
[`required-release-gates.json`](../../eng/acceptance/required-release-gates.json), not by
a historical fixed job count. See [publishing](../publish.md).
