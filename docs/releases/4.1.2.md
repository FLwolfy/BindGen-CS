# BGCS 4.1.2

## Browser execution admission

The optional BrowserWasm profile admits DllImport and LibraryImport. It rejects
FunctionTable with an actionable diagnostic before replacing existing output.
Trimmed Mono Wasm interpreter indirect calls require runtime signature cookies;
a static function address does not establish their availability. A standalone
reproduction without BGCS fails at the same runtime boundary, while both import
controls preserve the exact high-bit UInt64 result.

The policy belongs to the Browser extension. The generator neither inspects
consumer AOT options nor adds unused imports to influence the runtime signature
table. Desktop FunctionTable support and the public extension ports are retained.

## Browser cache inputs

The official target provider now implements the standard cache fingerprint
contract. Its implementation, selected compiler installation file and adjacent
SDK version manifest are included, with tracked absence. Existing frontend
snapshots continue to own header content, search order/membership, sysroot,
macros, arguments and language. Resolution no longer depends on an untracked
C++ directory-existence branch. Incomplete third-party fingerprints still
disable affected cache reuse.

## Verification and requirements

Regressions cover unchanged reuse, input invalidation, cancellation, conflicting
triples, unsupported-mode refusal and preserved published output. The existing
browser gate runs trimmed interpreter and AOT consumers for both admitted
imports, including exact UInt64/mixed signatures, reverse callbacks, anonymous
aggregate adapters and context lifetime admission.

Four same-revision generator/product gates and independent candidate/public
package consumption remain required. Passing receipts are published separately;
these notes do not certify a pending run. LLVM, .NET, model revision and consumer
build ownership remain unchanged. Previous tags and package bytes are immutable.
