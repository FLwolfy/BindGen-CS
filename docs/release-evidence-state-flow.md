# Implementation review and release evidence

The automatic workflow chain is `CI` → `Product package certification` → `Publish BGCS NuGet`. The last workflow authenticates its triggering run through GitHub's API and the exact workflow ID/path, repository, main branch, event and successful conclusion. It derives the candidate from the product run's exact source association and validates the downloaded receipts; `workflow_run.head_sha` alone is not a package source identity. A newer main revision, newer failed/in-progress rerun, missing/skipped/duplicate job or stale artifact prevents tag creation.

After the existing complete release preflight and fresh physical consumption, the publishing job rechecks the current main head, latest accepted CI/product runs, required gates and package hashes. It creates `v<version>` only for that commit; an existing tag must resolve to the same commit and is never moved. NuGet publishing, public indexing/payload checks, clean four-product installation and GitHub release publication continue in that same job. This follows GitHub's documented [workflow_run trust boundaries](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run) and [GITHUB_TOKEN trigger behavior](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow): creating a tag with that token does not start a second push workflow. Pure `node --test scripts/test-release-workflow.js` controls exercise these rejection and ordering rules without contacting GitHub.

The checked-in inventories describe reviewed work and the tests that must prove it. They cannot contain a receipt for a commit that has not yet been created. Certification is an output of CI and release preflight, with the exact source revision and file content digest, rather than a checked-in promise.

1. During implementation, feature rows remain `pending` or `inProgress`, configuration rows remain `pending`, and `implementation-status.json` keeps `implementationReady: false` and `releaseReady: false`. `implementationMapping`, source retirement hashes and dirty local test receipts document progress; they never certify parity.
2. Review each implemented feature and every frozen configuration row individually. Its source declaration becomes `status: "implementationReady"` only after it names existing neutral implementation files, exact fully qualified test methods, required hosts, and an `acceptanceRationale` explaining the assertions. Every test mapping also declares `requiredCases`: the exact literal TRX display names, including theory arguments. The actual matched cases must equal this unique set and all pass; one import-mode row cannot certify a six-mode matrix, and one unrelated grouped fixture cannot replace the selected option's assertions. A finite host scope also needs `scopeJustification`. A feature may instead require a named structured acceptance category; configuration rows always require exact test methods. This review must distinguish a new safe policy from an unchanged feature and explain the exact replacement behavior. No script promotes rows from source correspondence automatically.
3. Set the inventory-level `implementationReady: true` only after that complete review. Keep checked-in `releaseReady: false`. Run `python scripts/verify-feature-release-evidence.py --check-readiness` to check the declarations before committing. This command needs no CI receipt, produces no certification artifact, and cannot be combined with receipt inputs or `--output`. All 64 feature identities and the frozen 243 configuration identities remain in their respective inventories; the configuration baseline can only be extended after its unchanged prefix.
4. Commit the reviewed declarations together with the implementation. Clean CI builds this commit and executes all required gates. Host reports record actual TRX hashes, executed method outcomes, structured categories, source revision and content digest. A missing test, skipped case, failure, dirty checkout, prebuilt-output substitution, different source content or missing required host blocks certification even when the source declaration says `implementationReady`.
5. `verify-feature-release-evidence.py --revision <commit> --archive <host-report.zip> ... --output <proof.json>` joins the complete same-revision host reports with the reviewed declarations. A successful result has `featureAcceptanceVerified: true` and per-row `status: "verified"`, while its `releaseReady` remains `false`: desktop feature evidence alone does not cover every release gate. Old checked-in `status: "complete"`, `status: "verified"` or `releaseReady: true` claims are rejected as shortcuts.
6. Release preflight checks every required CI job, the derived feature/configuration proof, complete installed products on all declared hosts, and the dedicated Visual Studio 2026 TaskHost evidence. Only after all these checks succeed does it write a separate `artifacts/release-preflight/readiness.json` with `releaseReady: true` for that exact commit. It preserves this result and the feature proof as workflow artifacts. The source inventories are not rewritten.
7. Publishing still has its own requirements: build and verify the physical products, attest the delivered bytes, push the four products, verify NuGet indexing and downloaded payload hashes, and run clean public-source installation checks. A preflight result authorizes this release attempt; it is not evidence that publication has already happened.

If implementation, test mapping, configuration, toolchain lock or release requirements change, create a new commit and obtain its receipts. Previous local or CI results remain historical evidence and cannot certify the new revision. Green source tests alone do not imply platform, installation or NuGet publication certification.

`readiness-review-candidates.json` is a separate review input, with shared `testReviews` and `declarationReviews` so literal theory cases are recorded once. It never rewrites either inventory. Inspect an expanded proposal with `python scripts/readiness_review_candidates.py --feature output.source-patch-and-regex-processing` or `--configuration CFG0116`. Expansion preserves every host, exact method, literal case and proposed state; it does not remove a recorded gap or promote an `inProgress` proposal. The reviewer must still examine the group's assertions and limitations before copying any declaration. `python scripts/test-readiness-review-candidates.py` checks these reference-preservation rules with review-only fixtures.

The `validation.desktop-wasm-and-nativeaot` feature uses the finite global proof ID `desktop-browser-nativeaot` on every launch host. It cannot be filled with an unrelated Host test or category. `required-release-gates.json` declares exact independent job names and installed report IDs. Release preflight obtains successful, completed, non-skipped CI and package job observations through the authenticated GitHub API, downloads every required product artifact, and binds its actual archive hash to those observations. The verifier independently checks all contained report hashes, clean source/content identities, complete NativeAOT aggregate checks, browser interpreter/AOT calls, nonblocking lifecycle checks, import modes and execution closures. It also requires the dedicated TaskHost artifact. The package workflow's default-branch run SHA cannot replace the source identity inside those actual reports.

For a manual audit of already downloaded trusted evidence, run the certification command with `--workflow-evidence <observations.json>` and one `--product-archive <exact-artifact-name>=<zip-path>` for every declared product artifact, in addition to the host `--archive` arguments. The workflow creates these observations from the accepted runs; a pre-asserted `verified: true` JSON object is not a global proof input. Regression commands are `python scripts/test-feature-release-evidence.py`, `python scripts/test-global-feature-evidence.py`, and `python scripts/test-ci-product-evidence.py`. Their synthetic fixtures test the verifier and never count as product execution.
