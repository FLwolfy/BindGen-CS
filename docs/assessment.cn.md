# 架构与产品评估

设计性质与执行认证分开。4.0 当前证据由 records/acceptance 索引，并须对应源码和实际包；历史 3.x 回执仅作为回归参考。

| 维度 | 设计与审查依据 | 真实限制 |
| --- | --- | --- |
| 功能 | C/C++ 事实、类型化桥接、三种 import、raw/friendly、两种 Runtime 交付与 61 项保留功能。 | 不靠猜测支持任意 C++、隐含所有权或未知 ABI。 |
| 代码清晰与维护性 | descriptor 统一身份；调用与转换计划携带不变量；复核实际最终产物。 | 协调流程和复杂 C++ 协议仍需认真审阅，文件小不等于质量高。 |
| 架构整洁 | Core/Runtime 独立；Engine 与默认组合分开；具体实现位于中立模块之外。 | 已复现的表达缺口仍可能要求最小核心契约增量。 |
| 可拓展性 | 普通接口、独立 target/runtime/ABI、lowering、projection 和 Runtime provider。 | 注册名称不会创造运行环境、ABI 证明或缺失的生命周期协议。 |
| 使用简易性 | BGCS 自带基础能力，一个 CLI 命令或 C# 入口即可生成。 | SDK 头文件、模板选择和库语义仍是必要输入。 |
| 解耦性 | Native → Bridge → Interop → Managed → emission；worker 隔离；生成期与运行期闭包分离。 | 替换 frontend 需要等价事实；消费项目必须遵守源码要求。 |
| 跨平台能力 | 宿主资源、目标 SDK/布局、runtime、调用 ABI 分开，未知组合明确失败。 | 资源可用、生成成功与真实调用分别记证据，不能合并宣传。 |

## 通常只需扩展的需求

SDK 路径、宏和目标规则交给 target provider；已有模型可表达的调用规则交给 ABI provider；执行约束交给 runtime provider；库资源协议交给语义配置/lowering；模块加载、配对分配和释放调度交给 Runtime 接口。

三组独立 provider fixture 使用同一个 Engine，不引用基础平台实现。Inline、目标、调用 ABI 和 lowering 示例展示不发布插件也能直接注册代码。测试源码只有实际执行之后才成为验收证据。

## Runtime 为何独立

应用需要原生调用与资源存活辅助，不需要 parser、SDK 发现或生成基础设施。module lease 保护活动调用、对象、回调和异步任务仍需要的代码。源码 Runtime 是另一种交付方式，不是另一套生命周期算法。

## 仍然存在的边界

新的语言结构、物理调用传输或未建模生命周期，可能需要核心契约修改。SDK/编译器变化和普通缺陷，即使 .NET 不升级，也可能需要修复。稳定维护意味着变更有证据、通常局部化，不意味着核心永远不可改变。

消费项目、业务 facade、SDK 安装、构建 provider、MSBuild Task 和部署系统均不属于产品。保留适用许可证、准确标注未验证平台是交付责任，不是旧版兼容。
